## 一、开发环境搭建

### 1.1 Python 环境管理
- 版本选择：生产环境推荐 Python 3.10 或 3.11，兼顾生态兼容性与性能。
- 虚拟环境工具：
  - `venv`：标准库自带，轻量场景首选。创建：`python -m venv .venv`，激活后用 `pip install -r requirements.txt` 安装依赖。
  - `conda`：科学计算场景常用，可管理非 Python 依赖（CUDA、MKL）。创建：`conda create -n ai python=3.11`。
  - `uv` / `poetry`：现代依赖管理工具，锁定版本保证可复现构建。
- 依赖冻结规范：训练环境必须导出 `requirements.txt` 或 `environment.yml` 并纳入版本控制；关键深度学习库组合参考：`torch==2.x` 与 `torchvision` 需小版本对齐，避免 CUDA 运行时不匹配。

### 1.2 GPU 驱动与 CUDA
- 显卡驱动决定可用的 CUDA 上限：驱动 ≥ 525 支持 CUDA 12.x。
- PyTorch 官方安装命令需指定 CUDA 版本，例如 `pip install torch --index-url https://download.pytorch.org/whl/cu121`。
- 验证 GPU 可用：`python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"`。
- 显存估算经验公式：训练显存 ≈ 模型参数量 × (权重字节数 + 梯度字节数 + 优化器状态字节数) × 批大小相关系数。以 AdamW+FP16 为例，7B 参数模型全量微调约需 84GB 以上显存，因此大模型通常采用 LoRA 微调或量化。

### 1.3 容器化开发环境
- 基础镜像选择：`pytorch/pytorch:2.x-cuda12.1-cudnn8-devel`（训练）或 `-runtime`（推理）。
- Dockerfile 最佳实践：固定基础镜像 tag；先复制并安装依赖文件再复制代码，利用层缓存；设置 `PYTHONUNBUFFERED=1` 保证日志实时输出。
- docker-compose 中为训练服务配置 `deploy.resources.reservations.devices` 挂载 GPU（需要 nvidia-container-toolkit）。

## 二、数据工程

### 2.1 数据采集与合规
- 数据来源分级：公开数据集（ImageNet、COCO、中文 CLUE 等）＞企业自有数据＞爬取数据。使用爬取数据必须核查 robots 协议与版权、个人信息保护法（PIPL）要求。
- 个人信息脱敏规范：姓名、手机号、身份证号等字段必须替换为哈希或假名；训练日志禁止打印原始用户内容。

### 2.2 数据清洗流程
1. 去重：精确去重（hash）＋模糊去重（MinHash/SimHash），文本语料重复率建议控制在 5% 以内。
2. 缺失与异常值处理：数值特征用中位数/分箱填充；类别特征单独设 "unknown" 类别；时间序列异常用滑动窗口 3σ 法检测。
3. 标签质量：采用 K 折交叉标注一致性检验（Cohen's Kappa ≥ 0.7 视为可靠）；噪声标签可用 Confident Learning 清洗。
4. 数据划分：严格 train/val/test = 8:1:1 或 7:2:1；分类任务用分层抽样；时间序列按时间切分防止未来信息泄漏。

### 2.3 特征工程
- 数值特征：标准化（Z-score）用于线性模型与神经网络；树模型无需归一化。
- 类别特征：低基数用 One-Hot；高基数用 Target Encoding（须在验证折内拟合防泄漏）或 Embedding。
- 文本特征：TF-IDF 适合传统模型；深度模型直接使用子词分词器（BPE/WordPiece）。
- 特征存储：生产环境推荐 Feature Store（Feast）统一离线/在线特征，避免训练-服务偏差（training-serving skew）。

## 三、模型训练与调参

### 3.1 训练基线方法
- 先建立简单基线：分类任务先用逻辑回归/XGBoost，再用深度模型超越它；若深度模型不如基线说明数据量或特征不足。
- 过拟合诊断：训练损失持续下降而验证损失回升即过拟合；对策依次为数据增强、正则化（L2/Dropout）、早停、减小模型容量。
- 欠拟合诊断：训练与验证损失都高且接近；对策为加大模型、增加特征、延长训练、降低正则化强度。

### 3.2 超参数调优
- 学习率是最重要超参：常用搜索范围 1e-5 ～ 1e-2（对数刻度）。Transformer 微调典型值 2e-5～5e-5。
- 调参策略优先级：随机搜索 ＞ 网格搜索；样本充足时用贝叶斯优化（Optuna/Hyperopt）；每次实验必须记录配置与指标（MLflow/W&B）。
- 学习率调度：Warmup + 余弦退火是 Transformer 训练标配；warmup 步数取总步数的 6%～10%。
- 批大小与学习率线性缩放法则：批大小扩大 k 倍，学习率可同步扩大 k 倍（存在上限）。

### 3.3 分布式训练要点
- 数据并行（DDP）：最常用，每卡完整模型副本，梯度 AllReduce 同步。启动：`torchrun --nproc_per_node=8 train.py`。
- 混合精度训练：FP16/BF16 自动混合精度（`torch.cuda.amp`）可省约一半显存并提速 1.5～2 倍；BF16 数值范围更大更稳定，Ampere 及以上架构优先。
- 梯度累积：显存不足以容纳大 batch 时，用小 batch 累积梯度等效放大，`accum_steps × micro_batch_size = 目标 batch`。
- ZeRO/张量并行：单放不下时用 DeepSpeed ZeRO-2/3 切分优化器状态与参数，或 Megatron 式张量并行。

### 3.4 常见训练问题排查
| 现象 | 可能原因 | 处置 |
|---|---|---|
| loss = NaN | 学习率过大 / FP16 溢出 / 数据含脏值 | 降低 lr、换 BF16、清洗数据、梯度裁剪(max_norm=1.0) |
| loss 不下降 | 标签错位 / lr 过小 / 输入未归一化 | 检查 dataloader 对齐、调大 lr、检查预处理 |
| 验证集远好于训练集 | 数据泄漏 / 验证集太小 | 检查切分方式与时间先后 |
| GPU 利用率低 | dataloader 瓶颈 | num_workers 调大、prefetch、解码放在 GPU |

## 四、模型压缩与推理加速

### 4.1 量化
- PTQ（训练后量化）：INT8 量化一般掉点 <1%，配合校准集（500～1000 条代表性样本）效果更稳。
- QAT（量化感知训练）：掉点敏感场景使用，训练时插入伪量化节点。
- 大语言模型量化：GPTQ/AWQ 4-bit 权重量化可将 7B 模型压到约 4GB 显存可跑；GGUF 格式配合 llama.cpp 支持消费级显卡/CPU 推理。

### 4.2 蒸馏与剪枝
- 知识蒸馏：学生模型学习教师模型 soft label，损失 = KL(teacher||student)×T² + CE×(1−T)，温度 T 常取 2～5。
- 结构化剪枝：按通道 L1 范数裁剪后 finetune 回精度；非结构化剪枝需要专用硬件/稀疏算子支持才有收益。

### 4.3 推理优化
- ONNX Runtime：通用 CPU/GPU 加速，`torch.onnx.export` 后用 ORT 会话执行，动态 batch 提升吞吐。
- TensorRT：NVIDIA GPU 极致优化，FP16/INT8 引擎构建后延迟可降 2～5 倍。
- vLLM/连续批处理：LLM 服务主流方案，PagedAttention 显存管理使吞吐较原生 HF 提升 5～10 倍。
- 服务端 batching：动态合批（max_batch_size、max_queue_delay 两个参数权衡延迟与吞吐）。

## 五、部署上线

### 5.1 服务化框架选型
- REST（FastAPI/Uvicorn）：通用易调试，适合中低 QPS 与多模态接口。
- gRPC：内部服务间高性能通信，protobuf 强类型契约。
- Triton Inference Server：多框架模型统一托管，内置动态批处理与模型仓库版本管理。
- 模型即 API 的超时规范：常规推理接口 P99 延迟建议 <800ms；流式接口首 token 延迟 <2s。

### 5.2 发布流程规范
1. 离线评测达标（准确率/召回率/F1 不低于上一版 −0.5%）方可进入预发。
2. 影子模式（shadow deployment）：新模型接收真实流量但不返回用户，对比线上表现至少一周。
3. 灰度发布：按 5% → 20% → 50% → 100% 流量放量，每档观察核心业务指标 24 小时以上。
4. 回滚预案：保留上一版本镜像与模型工件，回滚时间目标 <15 分钟。

### 5.3 配置与密钥管理
- 模型路径、阈值、API Key 一律走环境变量或配置中心，禁止硬编码进镜像。
- 密钥轮换周期 ≤90 天；日志脱敏规则覆盖 token、手机号、身份证。

## 六、监控与持续运维

### 6.1 指标体系
- 系统层：QPS、P50/P95/P99 延迟、GPU 利用率、显存占用、错误率。
- 模型层：线上准确率（延迟标签场景用代理指标如点击率/转化率）、置信度分布漂移、特征漂移 PSI（Population Stability Index >0.25 触发告警）。
- 业务层：人工复核抽检合格率（建议每日抽检 ≥200 条）、用户负反馈率。

### 6.2 数据与概念漂移
- 协变量漂移：输入分布变化，PSI/KL 散度监控。
- 概念漂移：输入不变而 P(Y|X) 变化，需定期（月级/季度级）用新标注数据重训。
- 重训触发条件：指标跌破阈值、漂移告警、或累计新标注数据达原训练集的 20%。

### 6.3 事件响应
- 分级：P0 服务不可用（15 分钟内响应）、P1 指标严重劣化（1 小时）、P2 一般异常（1 个工作日）。
- 复盘模板：时间线、根因（5 Whys）、影响面、修复动作、防复发清单。
