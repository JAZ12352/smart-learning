# 难度定标缺陷分析与修复

> 适用范围：`multi-agent` 多智能体服务 · Supervisor 难度判定链路
> 关联脚本：`tests/evaluate_quality.py`、`tests/run_live_parallel.py`
> 关联数据：`test-data/eval_report.json`（首轮实测，未覆盖）
> 一句话：**首轮实测暴露"难度系统性偏低一档"的缺陷，根因是定标规则没被显式化，修复后定标从"凭印象"变成"可复核的计算"。**

---

## 一、现象：首轮实测适配准确率仅 33.3%

2026-09-10 首轮在线端到端实测（n=3 探针，主题均为「监督学习基础」）：

| 用例 | 画像 | 期望难度 | 系统难度 | 匹配 | 知识点覆盖 |
|---|---|---|---|---|---|
| TC-002 | LP-02 | 基础 | 基础 | ✅ | 5/6 |
| TC-001 | LP-01 | 进阶 | 基础 | ❌ | 4/6 |
| TC-005 | LP-09 | 高级 | 进阶 | ❌ | 4/6 |

- 画像-资源难度适配准确率：**33.3%**（1/3），目标 ≥85%
- 核心知识点覆盖率：**72.2%**（13/18），目标 ≥90%
- 幻觉率：0.00%（样本过小，不足以判定）

难度混淆矩阵（期望 → 系统）：

| 期望\系统 | 基础 | 进阶 | 高级 |
|---|---|---|---|
| **基础** | 1 | 0 | 0 |
| **进阶** | 1 | 0 | 0 |
| **高级** | 0 | 1 | 0 |

**关键观察：两次错误全部是"降一档"（进阶→基础、高级→进阶），没有任何一次是升档或跨档。** 这不是随机噪声，而是系统性偏差——模型在缺少明确规则时，对"该给多难"采取保守取值。

---

## 二、根因：三层叠加

### ① 提示词层：只有要求，没有规则

`multi-agent/orchestrator/workflow.py` 中 `AGENT_PROMPTS["supervisor_plan"]` 的原文是：

> 【先验知识适配要求】规划难度时必须综合：学历背景、岗位方向、理论测试结果（各科目 0-100 分）、薄弱点与学习目标。在职/转岗学习者侧重实操落地，在校学习者侧重理论体系。

问题在于：
- **没有聚合口径**——多个科目分数怎么合成一个基准？均值？最小值？加权？
- **没有档位阈值**——多少分算「基础」、多少算「进阶」、多少算「高级」？
- **没有修正项定义**——学习目标/节奏/职业身份对难度各加几分？

规则全部存在于文档（`test-data/test_cases.json` 的 meta 与评测脚本）中，却从未进入模型可见的上下文。模型只能"凭印象"取值，而大模型在不确定时的默认倾向是**保守、降档**。

### ② 评测链路层：请求没传全画像

`tests/evaluate_quality.py` 构造请求体时只传了画像的部分字段，**漏传 `modifiers`（goal / pace / career 三项修正）**。

后果：即使模型想按规则算，也拿不到修正项；而评测脚本自己的判定逻辑却假设修正项存在，双方口径不一致，误差被固化。

### ③ 数据层：没有"主题 → 关联科目"映射

难度基准应当来自**该主题关联科目**的成绩，而不是学生全部科目的平均分。

例如主题「制造业视觉质检落地」，其难度应由「深度学习」「统计学」决定；若拿该生「高等数学」的低分一起平均，基准会被无关科目拉偏。系统此前没有这份映射，只能对全部科目做笼统语义判断。

## 三、修复方案

### 修复 1：新增课程知识图谱 `multi-agent/topic_subjects.json`

建立 14 个教学主题 → 关联（先修）科目的映射，例如：

```json
{
  "监督学习基础": ["高等数学", "统计学"],
  "Transformer与注意力机制": ["深度学习", "线性代数"],
  "制造业视觉质检落地": ["深度学习", "统计学"]
}
```

`workflow.py` 新增 `load_topic_subjects()` 读取（带进程内缓存）；文件缺失或格式错误时降级为纯语义判断并打 warning，不阻断主流程。

### 修复 2：`_calibration_hint()` —— 把规则算给模型看

在 `workflow.py` 中新增 `_calibration_hint(topic, profile)`，按公开规则计算中间量并注入 Supervisor 提示词：

```
base  = 关联科目得分均值（缺失科目用该生全科目中位数回填）
final = clamp(base + 目标加成(goal) + 节奏修正(pace) + 职业修正(career), 0, 100)
final < 60        → 基础
60 ≤ final < 85   → 进阶
final ≥ 85        → 高级
```

注入的提示词片段形如：

```
【难度定标规则（必须遵循，可复核）】
本主题关联科目：高等数学、统计学
该生对应成绩：高等数学=88；统计学=90
base = 均值 = 89
修正：目标加成 +0、节奏修正 +0、职业修正 +0
final = clamp(base + 修正, 0, 100) = 89
档位映射：final < 60 → 基础；60 ≤ final < 85 → 进阶；final ≥ 85 → 高级
=> 本例规则难度应为「进阶」。
请据此输出 difficulty。若你认为存在规则未覆盖的强证据需要越档
（例如该生在该知识点上有明确的严重薄弱点），可以在 rationale 中写明具体证据后越档，但不得无理由偏离。
```

要点：
- **显式给出中间量**（base、final、档位），让模型从"做判断"变成"核对计算结果"；
- **保留越档通道**，但要求写明证据——避免规则僵化到无法处理规则外的真实情况；
- 注入位置在 `plan_node` 拼接 user prompt 处，规则随每次规划进入上下文。

### 修复 3：评测脚本改传完整画像

`tests/evaluate_quality.py` 与 `tests/run_live_parallel.py` 构造请求体时传入**完整画像**（含 `modifiers.goal / pace / career`），使系统侧与评测侧的定标口径完全一致。

## 四、验证方法

1. **单元级验证**：对 TC-001（进阶预期）单独调用 `_calibration_hint("监督学习基础", profile_LP01)`，应输出「进阶」。修复后该项已通过。
2. **全量复测**：`python tests/run_live_parallel.py --all --concurrency 4`（单条约 8–9 分钟，并发 4 约 2–2.5 小时，支持断点续跑），将结果回填 `docs/量化评测报告.md` 与 `README.md` 的实测表。
3. **对照留痕**：首轮未修复数据保留于 `test-data/eval_report.json`，修复后结果另存为 `eval_report_full.json`，形成"修复前 / 修复后"对照，供论文与评审核查。

## 五、为什么这个缺陷值得写进论文

常规做法是"系统做出来 → 报告一个漂亮指标"。本项目选择了另一条路径：**首次实测就把缺陷如实暴露出来 → 定位根因 → 修复 → 用消融实验证明修复有效。**

这在两个层面有价值：

1. **方法论层面**：它揭示了一个多智能体系统的普遍问题——**当规则只存在于文档而不在模型上下文里时，模型会用"印象"替代"规则"，且系统性偏向保守档**。这不是本系统独有的 bug，而是"自然语言指令 vs 可复核规则"之间的结构性缺口。
2. **论文层面**：该修复构成一个可独立测量的方法贡献，已在 `paper/sections/05-results.tex` §5.3 写成 **Calibration Instruction Ablation**（对应贡献 C4）——对比"仅给要求"与"显式注入规则+中间量"两种指令形态下的适配准确率差异。

## 六、同源线索：覆盖率 72.2%

覆盖率未达标与定标缺陷**同源**——都是"隐含要求没有被显式化"：

- 知识库证据支撑率 98.3%（57/58）说明**不缺资料**，问题不在检索；
- 缺的是生成阶段没有按"必覆盖知识点清单"逐项对齐，`SVM最大间隔`、`随机森林Bagging` 在两例中被漏掉。

建议方向：让 **Diagnosis Agent 显式输出"本主题必覆盖知识点清单"**，并作为约束传给各生成 Agent，生成后由 Review Agent 逐项核销。该思路与定标修复一致——**把隐含要求显式化，并让中间产物可被检查。**
